# A計畫維修料件管理系統｜系統化規劃書 v2

基準版本：**`A計畫 自動帶入版 V2.6.5`**（Excel，23 個頁籤）
目標：把這本 Excel 改寫成**獨立的**線上系統，沿用現有客服記錄系統的技術棧與開發規範。
狀態：規劃草案，待確認後才進入開發。

## 1.2 為什麼基準是 V2.6.5

V2.6.4 與 V2.6.5 的差異只有三處，頁籤結構、公式架構、異常項目數量完全相同：

| 項目 | V2.6.4 | V2.6.5 |
| --- | --- | --- |
| 驗收記錄 J 欄 | 未用 > 領料 → `⚠未用大於領料` | → `請確認數量`（**不再視為異常**） |
| 案件總表 N 欄 | 含 `⚠驗收異常` 判定 | 移除，直接計算領料數減未用數 |
| 工班退料差異頁 | — | 新增說明：未用大於單筆領料僅為資料確認，不列異常、不要求逐車修正 |

**V2.6.5 這個改動是有意義的政策決定**，且與核心原則一致 —
對帳既然以工班＋品項總量為準、不追哪一案件，單筆未用大於領料就不該擋人，提示即可。
系統照這個政策做（見規則第 6 條）。

## 1. 一句話結論

不要再維護第二本 Excel。A計畫 做成**獨立系統**，但沿用現有客服記錄系統已驗證過的
技術棧與開發規範（Supabase + 靜態前端模組 + report-api）。
**Excel 裡每一條公式改寫成資料庫 View，人只填「該由人填的欄位」，其餘全部由系統推導。**

現在 Excel 內的資料列幾乎是空的（除品項主檔約 24 筆），
沒有歷史資料轉檔負擔，是搬家成本最低的時間點。

## 1.1 已確認的前提

| # | 決定 | 對規劃的影響 |
| --- | --- | --- |
| 1 | **獨立系統**，不併入客服記錄系統 | 獨立 repo、獨立網址、獨立資料表；技術棧與開發規範照抄現有專案 |
| 2 | **退料對帳與請款財務彼此獨立**，沒有先後順序 | 改為「共用底座＋兩軌並行」，哪一軌先上線都可以 |
| 3 | **驗收不做手機版** | 省掉離線暫存與重送機制，驗收頁只做桌面版 |
| 4 | **筋斗雲先不做 API** | 四個來源全部走貼上／上傳；API 保留為後續加值項目，屆時只加同步層，不動資料表 |
| 5 | **Excel 不再作為作業工具** | V2.6.5 不修了，改當系統規格的實證來源；過渡不再雙軌並行（見第 8 節） |
| 6 | **驗收缺日期顯示「⚠缺驗收日期」** | 不算已驗收。有數量無有效日期，狀態就停在缺日期 |
| 7 | **新制判定一律以領料日為準** | 退料責任跟著領料走；驗收日與登記日可補填，不適合當基準 |
| 8 | **月結確認結果為「相符／不相符」** | 只有「相符」能往下走到 ERP 修正與交財務 |
| 9 | **登入帳號與客服記錄系統共用同一組** | 不必記兩組密碼；A計畫 的資料表另外做角色權限控管 |
| 10 | **角色名單**：客服 Emily／倉庫 Alan／管理者 Emily／維修工程師未定 | 見第 11.2 節，其中「維修工程師未定」會直接影響上線（見 11.3） |

### 對第 2 點的一項修正

「沒做退料核對也不會影響月結與財務交接」— 這是對的，退料對帳確實不影響請款流程。
但**驗收登錄是兩軌共用的**：一般案件收費確認頁的「可提供財務」判定，
第一個條件就是驗收狀態必須為「已驗收」（未驗收會停在「待驗收」，不會進財務清單）。

因此驗收放在**共用底座**，不歸在退料那一軌。退料對帳（工班差異、總量對帳）才是可以完全獨立的部分。

### 2.2 現有系統端（本 repo）

- 前端：靜態 HTML + 模組化 JS（`客服記錄系統.*.js`），GitHub Pages 部署
- 資料：Supabase Postgres，已收斂 RLS 為 authenticated only，具 `activity_log`
- 匯出：`report-api`（Render）產生週報／月報 Excel
- 規範：`AGENTS.md`、`RULES.md`（RLS 不得放寬、每次異動要寫 activity_log、SQL 需附 rollback）

**結論：A計畫 是獨立系統，但技術棧不需要新增任何東西 —
同一套 Supabase、同樣的靜態前端模組寫法、同樣的開發與備份規範，直接沿用。**

### 2.3 「獨立」到什麼程度

| 項目 | 做法 | 理由 |
| --- | --- | --- |
| 程式碼 | **獨立 repo**（例如 `a-plan`），不放在 `repair-form` 內 | 兩套系統各自部署，改一邊不會影響另一邊 |
| 網址 | **獨立網址**（各自的 GitHub Pages） | 使用者從不同入口進，不會誤操作 |
| 資料表 | **完全獨立**，不與客服案件表共用 | 兩邊的案件定義不同，不該混在一起 |
| 登入帳號 | **共用同一組**（已確認） | 同一批人不必記兩組密碼；權限在 A計畫 的資料表上另外切 |
| 開發規範 | 沿用 `AGENTS.md` / `RULES.md` | RLS、activity_log、SQL rollback 規則照舊 |

## 3. 為什麼要離開 Excel（風險都有具體出處）

| # | 風險 | 具體出處 | 後果 |
| --- | --- | --- | --- |
| 1 | 列位鏡射 | 月結確認頁 `A2 = 新竹物流月結明細匯入!W2`，直接綁列號；SOP 第 12 條寫明「禁止插入列、刪除列或排序」 | 一旦有人排序，整頁金額對到別的報修單，而且**不會報錯** |
| 2 | 唯一 key 會漂移 | 領料單 `AB2 = B2 & "-" & COUNTIF($B$2:$B2,$B2)` 是累計序號 | 重貼、補貼、刪列都會讓 key 改變，歷史驗收記錄會對到別的案件 |
| 3 | 列數上限 | 各頁 2000 列（SOP 自述約 10 個月）、ERP 與月結區僅 600 列 | 明年就要再開一本，跨檔對帳 |
| 4 | 綁死 Excel 365 | 使用 XLOOKUP／LET／FILTER／SORT／UNIQUE；SOP 明列 Google 試算表、WPS、Excel 2019 會大面積 `#NAME?` | 手機只能查閱不能輸入，工程師現場無法即時驗收 |
| 5 | 沒有欄位權限 | 全檔可寫 | 客服可以改到驗收數量，倉庫可以改到金額 |
| 6 | 沒有稽核軌跡 | 無異動紀錄 | 「差異怎麼從 3 變成 0」查不出來，與老闆「都不能少」的要求衝突 |
| 7 | 全檔重算 | 2000 列 × 多組 SUMPRODUCT／FILTER／動態陣列 | 資料一多，開檔與輸入都會卡 |

### 3.1 V2.6.5 使用者測試：從理論變成實證

第 3 節原本是推論。V2.6.5 的使用者角度測試把它變成了實證 —
14 個使用流程有 8 個不通過，逐項核對後共 9 個缺陷（完整根因見
`A_PLAN_V265_DEFECT_REPORT.md`）。

關鍵在於**這些缺陷的性質**：9 個裡有 7 個屬於兩種結構性問題，
而這兩種問題在資料庫系統裡是不可能發生的。

**性質一：同一條規則寫在兩個地方，兩邊不一致（5 個）**

| 缺陷 | 規則被寫在哪兩個地方 | 後果 |
| --- | --- | --- |
| D-02 驗收 | 狀態判定看「數量」，累計卻篩「驗收日期」 | 顯示已驗收，但不進應退量 |
| D-03 K 欄 | 列不列出用「關聯單號」，算多少用「退料歸屬」 | 工班整列消失 |
| D-04 無派工 | 總量對帳用「登記日」，工班差異要求「查得到關聯單號」 | 進得了總量，進不了工班對帳 |
| D-08 新制基準 | 工班差異用「領料日」，總量對帳用「驗收日／登記日」 | 資料填齊仍可能兩頁對不平 |
| D-06 月結 | 判定只看「有沒有填」，沒有人定義「填什麼才算數」 | 隨便打字就能推進到可交財務 |

**性質二：參照沒有約束，指向不存在的東西（2 個）**

| 缺陷 | 內容 |
| --- | --- |
| D-07 | 兩個品項下拉的來源寫 `品項主檔`，但頁籤實際叫 `品項主檔（維護）` — 下拉直接失效 |
| D-01 | 17 個首頁連結指向外部檔 `v249.xlsx`，內部頁籤名也全是舊短名 |

### 3.2 系統怎麼讓這兩類問題消失

| 缺陷 | 系統的結構性防護 |
| --- | --- |
| D-01 首頁連結 | 導覽是程式路由，不是儲存格連結。**不存在「連到別的檔案」這種故障** |
| D-02 驗收日期 | 驗收日期 NOT NULL；驗收狀態由單一 View 推導，判定與累計用同一份定義 |
| D-03 K 欄 | 列入條件與加總條件在 SQL 是**同一個 WHERE**，不可能一邊用 K、一邊用 M |
| D-04 無派工 | 無派工拆回時歸屬工班為必填，沒填就寫不進資料表 |
| D-05 單號填錯 | 關聯單號是外鍵，指不到既有案件就直接擋下，不會等到異常總覽才發現 |
| D-06 月結確認 | 確認結果是列舉值（相符／不相符），不接受自由輸入 |
| D-07 品項下拉 | 品項是外鍵指向品項主檔，**參照不存在的品項在資料庫層就不成立** |
| D-08 新制基準 | 「新制」寫成一個共用判定，兩張對帳表引用同一份，不可能分歧 |
| D-09 收費驗證 | 金額欄位型別即數值，收費／不收費為列舉值 |

剩下 2 個（D-05 的異常提示、異常總覽補列）在系統裡也不需要「補一列公式」—
它們是查詢條件，不是手工維護的清單。

**這一節的結論**：這次測試找到的不是「V2.6.5 沒做好」，
而是「用試算表做多表交叉對帳，必然會累積這類不一致」。
修完這 9 個，下一版加新欄位時同一類問題還會再出現。

## 4. 目標架構

```
外部來源              匯入層              資料層(Supabase)      推導層(View)         使用層
────────             ─────              ──────────────       ──────────         ─────
筋斗雲領料單 ──────┐
新竹物流報修 ──────┤
ERP訂單明細  ──────┼→ 貼上／上傳 ─────┬→ 原始事實資料表 ──→ 案件總表         ──→ 作業面板(每日待辦)
新竹物流月結 ──────┘  (欄位對應+去重   │   + 資料庫層檢核      退料差異／總量對帳    A軌：驗收/退料/對帳
                       +寫入前預覽)     │   + activity_log      月結／收費狀態        B軌：月結/收費/財務
辦公室輸入   ──────→ 表單(桌面版) ─────┘                       32 項異常         ──→ report-api 匯出 Excel

（日後要接筋斗雲 API 時，只在匯入層加一條同步路徑，資料層與畫面都不動）
```

三個設計原則：

1. **人只輸入原始事實，狀態一律由系統推導。**
   Excel 裡所有標示「(自動)」的欄位，一律不落地成資料欄位，改成 View 即時計算。
2. **檢核不靠人看，靠資料庫擋。**
   目前是「異常總覽亮紅字，人自己回去改」；系統改成寫入當下就擋掉（CHECK／UNIQUE／NOT NULL）。
3. **制度參數集中管理。**
   新制起算日、差異標準、舊案切點日目前散在儲存格裡，改成 `system_settings` 表，改動要寫 activity_log。

## 5. 資料模型（第一版）

### 5.1 基礎資料表

| Excel 頁籤 | 資料表 | 誰寫入 | 關鍵約束 |
| --- | --- | --- | --- |
| 品項主檔（維護） | `items` | 指定維護人員 | 料號唯一；停用不刪除（對帳要看得到歷史） |
| 筋斗雲領料單匯入 | `pick_lines` | 貼上／上傳 | 以「回覆編號＋品名＋數量＋領料時間」的內容雜湊做唯一索引擋重貼，**不用 Excel 那種 COUNTIF 累計序號**，補貼與刪列都不會讓 key 漂移；車號入庫即正規化 |
| 新竹物流報修匯入 | `repair_tickets` | 匯入 | (車號正規, 報修單號) 唯一 |
| ERP訂單明細匯入 | `erp_order_lines` | 匯入 | 續行訂單號補齊、金額文字轉數值在匯入層完成 |
| 領料單與ERP訂單對照 | `erp_manual_map` | 維修工程師 | 僅供自動比對不到時的人工例外 |
| 驗收記錄 | `acceptances` | 維修工程師 | `UNIQUE(pick_line_id)` 取代「⚠重複驗收」；`CHECK 0 <= 未用數 <= 領料數` |
| 月租返修品登記 | `rental_returns` | 維修工程師 | 來源＝本次派工拆回時，關聯單號 NOT NULL；登記日 NOT NULL |
| 工班退料批次登記 | `return_batches` | 維修工程師／倉庫 | 退料工班、退料歸屬 NOT NULL；`CHECK FAE正常+FAE異常 <= 返修品數` |
| 新竹物流月結明細匯入 | `settlement_details` | 客服 | 以報修單號為 key，不再依列位鏡射 |
| 新竹物流月結與金額確認 | `settlement_confirmations` | 客服 | 確認結果、ERP金額修正日 |
| 一般案件收費確認 | `general_charges` | 客服 | 是否收費、確認金額、確認日期 |
| 已提供財務紀錄 | `finance_handovers` | 交接人員 | ERP訂單號 + 提供日期 + 狀態 三者齊全才生效 |
| 新制起算日／差異標準／舊案切點 | `system_settings` | 管理者 | 異動寫 activity_log |
| —（新增） | `activity_log` | 系統 | 沿用現有表 |

**取代 Excel 唯一 key 的做法**：不再用 `回覆編號-序號`。
每筆領料明細用系統 UUID 當主鍵，另建業務鍵
`(回覆編號, 品名, 數量, 領料時間)` 的雜湊值做重貼偵測。
這樣補貼、刪列、重新匯入都不會讓歷史紀錄對錯案件。

### 5.2 推導檢視（View）

| View | 取代的頁籤 | 說明 |
| --- | --- | --- |
| `v_case_master` | 案件總表（進度追蹤） | 22 欄全部由 SQL 重現，不可手動輸入 |

## 6. 必須寫死進系統的 15 條業務規則

這些目前是 Excel 公式，搬進系統後要變成資料庫約束＋View＋前端阻擋。

1. **請款流程判定**：車號含「新瑞宅配」一律為一般案件；否則客戶名稱含「新竹物流」才走月結；其餘為一般案件。
2. **車號正規化**：TRIM 後去掉 `-`、半形空白、不斷行空白，入庫時就存正規化欄位並建索引。
3. **報修單配對**：以正規化車號 + 報修日 ≤ 領料日，取最大的報修日那筆。
4. **ERP 配對**：先查人工對照表；查不到則以品名「其他-車號」擷取車號比對。0 筆＝③未建單，>1 筆＝⚠多張ERP需人工補充。
5. **ERP 數量核對**：同訂單同品名數量合計 ＝ 領料數，否則⚠不一致。
6. **驗收計算**：實際使用 ＝ 領料數 − 實際未用數；未用數不可為負（負數擋下）。
   **驗收成立的條件是「未使用量 ＋ 有效驗收日期」兩者都有**；
   只有數量沒有日期，狀態停在「⚠缺驗收日期」，不算已驗收。〔V2.6.5 D-02〕
   **未用數大於單筆領料數時只提示「請確認數量」，不擋下、不列入異常**，
   因為對帳以工班＋品項總量為準，不要求逐車修正。〔V2.6.5 政策〕
7. **新舊制判定**：**一律以領料日**是否 ≥ 新制起算日（現為 2026-08-01）判定。
   所有對帳表共用這一個判定，不得各自用驗收日或登記日。〔V2.6.5 D-08〕
8. **退料對帳**：應退 ＝ 未使用 ＋ 月租返修；實退 ＝ 全新良品 ＋ 返修品；**差異必須為 0**。
9. **結案封鎖**：品項未建檔、驗收異常、差異 ≠ 0、工班未確認，四者任一成立即不可結案。
10. **月結金額**：按報修單號加總應付金額（不逐品項比對）；ERP「其他-車號」金額 − 月結金額 ＝ 0 才可交財務。
    **確認結果只有「相符／不相符」兩個值**，且只有「相符」能往下走到 ERP 修正與交財務。〔V2.6.5 D-06〕
11. **一般案件金額**：不收費 → 金額必須為 0；收費 → 金額 > 0 且等於 ERP 重匯金額。
    **0 元月租案件驗收完成後仍要進財務清單**（供扣庫存），但不開發票。
12. **財務交接**：同一 ERP 訂單不可同時出現在兩條流程；已提供財務者自動排除，需重送時才改為「允許重送」。

13. **退料列入條件**：新制退料是否列入工班對帳，**只看「退料工班」與「退料歸屬」**。
    關聯單號為選填，只供追溯與工班核對，**完全不影響列入與否**。〔V2.6.5 D-03〕
14. **無派工月租拆回**：月租例行拆回（無派工）必須指定歸屬工班，否則不可送出；
    指定後與一般拆回一樣納入工班對帳，不再只進總量。〔V2.6.5 D-04〕
15. **主檔參照**：品項、工班、關聯單號一律為參照主檔的外鍵，
    不接受自由輸入，也不可能指向不存在的來源。〔V2.6.5 D-07、D-05〕

上線前要跟你逐條對過一次，這 15 條就是驗收標準。
標註〔V2.6.5〕的五條，是這次使用者測試直接換來的規格。

### 7.5 時程總計

### 「八週」是什麼意思（v5 澄清）

前面各階段標的「週」，指的是**一個全職工程師的工作量**，合計約 40 個工作天。
這是發包或請人做時的估法，**不是日曆承諾**。

| 由誰建置 | 這個數字的意義 |
| --- | --- |
| 外部工程師或自僱人員 | 約 8 週全職工時，可直接當報價與排程依據 |
| **由 AI 協作建置（本專案的情況）** | 寫程式不是瓶頸，8 週應理解為「工作量的量級」，實際時程由下列三件事決定 |

由 AI 協作建置時，真正決定進度的是：

1. **規格對版**：15 條規則要逐條確認，需要你的時間。
2. **實際匯出檔樣本**：拿不到四份實際檔案，B2 的欄位對應就做不下去。
3. **你的測試與回饋**：像這次測 V2.6.5 一樣，每個里程碑都要測過才進下一個。

因此下方改以**里程碑**表示，不標日曆週。

### 里程碑與相依

| 里程碑 | 前置條件 | 完成的判準 |
| --- | --- | --- |
| M0 規格確認 | 15 條規則逐條對過 | 規格書確認，無待決事項 |
| M1 地基可跑 | M0| 可登入、可維護品項與制度參數、異動查得到是誰改的 |

### 「可以同時做完嗎」

可以。M4a 與 M4b 都只依賴 M3，彼此不相依，**兩者做完的總工作量相同**，
分不分批不影響總量，差別只在要不要提早開始用其中一邊：

- **分批上線**：M4a 完成就先用退料對帳，M4b 之後再上。早一點拿到部分效益，但要分兩次教學與驗收。

## 11. 角色、權限，與 Excel 的定位

### 11.1 Excel 與系統建置的關係

**V2.6.5 的業務邏輯是對的。** 缺陷報告裡的 9 個問題，沒有一個是業務邏輯錯 —

| 關係 | 有／沒有 | 說明 |
| --- | --- | --- |
| **規格來源** | ✅ 有 | 15 條業務規則、23 個頁籤的欄位定義、對帳口徑、異常判定，全部從 V2.6.5 抽出 |

### 11.3 「維修工程師未定」的影響（需要注意）

驗收登錄是**兩軌共用的底座**（B3），輸入者是維修工程師：

- **A 軌**：應退量來自驗收的未使用量 → 沒有驗收就沒有應退，工班差異算不出來。
- **B 軌**：一般案件要「已驗收」才可交財務 → 沒有驗收就卡在待驗收。

也就是說，**維修工程師人選未定會同時擋住兩軌的實際使用**，
不是只影響 A 軌，也不能拖到上線後再說。

1. **上線前確定人選**（最乾淨）。
